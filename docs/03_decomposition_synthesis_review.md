# 第 3 阶段代码审查：时序分解与合成

## 审查结论

本批代码已经覆盖论文中“结构分解—参数估计—逆向合成—质量验证”的主要方法链条，19 个正式特征也在 Notebook 中统一进入该流程。方法环节没有明显缺章，但工程上还不是可从头独立复现的 GitHub 主流程：最终执行版本散落在 Notebook 中，步骤间依赖未持久化的内存对象，并存在两个会影响运行或复现的明确缺陷。

因此，本轮将 14 个 Python 文件作为 `legacy` 原始模块归档，将清除输出后的 Notebook 作为当前最完整的实验记录。正式重构前，不把任一单个脚本称为“最终版”。

## 编号说明

原始文件没有 `step1_6.py`，并存在 `step1_4_5.py`。结合 Notebook 的实际章节和调用顺序，当前判断是研究期反复插入步骤造成的编号跳跃，并非缺少一个论文方法：GARCH 之后直接进入残差异常清洗、相关矩阵和边缘分布估计。

正式版建议不再使用 `step1_4_5`、`step1_7` 这类编号，而改为 `distributions.py`、`transformations.py`、`seasonality.py`、`event_effects.py`、`autoregression.py`、`volatility.py`、`residuals.py` 等语义化名称。

## 必须修复的问题

1. `step2_6.py` 将 `zero_injection_method` 默认设为 `None`，随后直接调用 `.startswith('threshold')`。调用方不显式传字符串时会触发 `AttributeError`；正式版应使用明确枚举和非空默认值，并在入口校验。
2. `step2_2.py` 的主入口接收 `seed`，但历史波动率分块重采样函数内部重新创建无种子的随机数生成器；同时主函数中的 `rng_global` 未使用。进入该兜底分支后，相同参数不能保证重复结果。
3. Notebook 固定使用 `C:\tongji\0 code\00_data\...`、固定输入文件名、固定训练日期与合成日期，离开原电脑不能运行。
4. 当前实际运行的 GARCH 与残差清洗是 Notebook 中的修改版 `run_step5_garch()` 和 `run_step7_clean_verify_v2()`，并非已导入脚本中的 `run_step5_garch_v3()` 和 `run_step7_clean_verify()`。单独上传脚本会产生“看似完整、实际版本不一致”的问题。
5. Prophet 脚本返回模型与预测对象，但合成阶段依赖的 `profile_<feature>.json` 由 Notebook 独有的 `extract_and_save_profiles()` 生成；缺少该函数时，`step2_5.py` 会静默以全零季节项继续运行。
6. GARCH 结果、AR 参数、变换参数、正常掩码、清洗后统计量和残差池主要通过 Notebook 内存传递。多数步骤虽然写出图和汇总 CSV，却没有统一、可重新加载的参数文件，因而无法从任意中间阶段恢复。
7. `step2_1.py` 无条件写 Parquet，但依赖说明此前没有 `pyarrow`；其他脚本对 Parquet 失败则直接忽略。正式版应统一为可选输出并记录失败原因。
8. 多个入口允许 `output_dir=None`，内部却直接创建目录；应统一要求路径对象或提供有效默认目录。
9. `step2_6.py` 对三个特殊特征直接读取 `target_stats['percentiles'][99]`，但该字段由 Notebook 独有的 `calculate_clean_stats()` 提供。缺失或格式不符时会触发 `KeyError`。
10. 全局 `warnings.filterwarnings('ignore')` 会隐藏拟合、数值稳定性和弃用警告，不适合正式复现流程。

## Notebook 中尚未模块化的关键内容

以下内容只存在于 Notebook，部分是完整运行所必需，而非单纯画图代码：

- `slice_data()`：统一日期切片；
- `extract_and_save_profiles()`：导出 Prophet 日内/周内季节模板；
- `run_step5_garch()`：实际执行的 GARCH 修改版；
- `run_step7_clean_verify_v2()`：实际执行的残差清洗、Pearson/Kendall 相关与异常记录版本；
- `build_global_normal_mask()`：从多特征异常记录构造正常时段掩码；
- `calculate_clean_stats()`：生成逆变换校准需要的 101 个历史分位点；
- `run_quality_validation()` 与 `calculate_numeric_quality()`：分阶段图形和数值质量评价；
- `detect_extreme_spikes()` 与 `fix_spikes_with_neighbor_mean()`：最终极端爆点检查与修复。

这些函数应先从 Notebook 抽离并建立输入输出契约，再编写总入口。Notebook 中另有多版逆变换、稀疏特征专用生成器和真实片段 bootstrap 覆写逻辑；其中多项未进入最终运行，建议移动到 `experiments/`，不要混入正式流程。

## 方法学与数据泄漏风险

1. 最终逆变换使用历史数据的 101 个分位点做秩映射，并对均值做强制校正。如果质量验证仍使用同一历史区间，分布与均值接近是校准机制的直接结果，不能作为独立泛化证据。
2. 建议按时间把真实数据分为参数拟合区间和保留验证区间。分布、相关矩阵、GARCH、AR、事件冲击、分位点和阈值只能由拟合区间估计；所有最终质量指标在未参与校准的保留区间上报告。
3. 验证器目前分别按真实数据与合成数据各自的分位点裁尾，这可能掩盖合成数据尾部过重或过轻。正式验证应优先使用由拟合区间真实数据确定的共同裁剪阈值，并同时报告未经裁剪的尾部指标。
4. 经验边缘分布、标准化残差池和历史条件波动率分块重采样都可能复现真实数值或局部片段。公开仓库不应包含这些中间产物；若声称数据可公开，还需增加最近邻距离、重复片段率或成员推断等隐私检查。
5. 最终“邻域均值修复爆点”会改变极值、ACF 和事件峰值。应记录每个特征修复点数、修复前后指标，并把它视为后处理而非生成模型本身的质量。
6. 事件显著性阈值、GARCH 风险特征列表、持久性阈值、软截断倍数和特征级例外目前是人工设置。应集中到配置文件并提供敏感性分析。

## 明显冗余或可下沉到实验区的内容

1. Notebook 包含 113 个代码单元，重复嵌入绝大多数脚本，并保留多版逆变换和大量调试单元；正式 Notebook 应只保留调用、关键图表和结果解释。
2. `step1_1.py` 与 `step1_2.py` 中部重复导入依赖，反映多个版本代码直接拼接；可在模块化时合并。
3. `step2_5.py` 导入 `model_from_json`，对应模型加载逻辑已整体注释，当前实际使用 JSON 季节模板；该导入可删除。
4. `step2_2.py` 的 `rng_global`、`step2_3.py` 的 `recovery_metrics` 等变量未被使用；静态检查还发现多处未使用导入和无占位符 f-string。
5. 特殊稀疏特征生成器、事件/背景 bootstrap 覆写和早期验证器已被注释或标为弃用，应放到单独实验记录并注明未进入论文主结果。
